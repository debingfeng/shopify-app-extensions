# Shopify App Template V4.0 技术需求文档

## 1. 文档定位

本文档用于定义 Shopify App 项目模板 V4.0 的技术需求范围，作为后续方案拆解、研发排期、联调验收和团队补充优化项的统一基线。

V4.0 的目标不是再次重做工程骨架，而是在 V3.0 已完成的环境治理、嵌入式壳层、配置统一和基础可运行能力之上，补齐以下三类运行时底座能力：

- 接入 `Web Vitals` 与安装链路性能观测
- 提供本地开发代理 server
- 标准化接入内部插件 `domDagic`

同时，文档预留“其他优化与问题处理”章节，用于团队补充 V4.0 周期内应一并纳入的稳定性、效率和规范性事项。

## 2. 背景

当前模板已经具备以下基础：

- `apps/admin` 已稳定运行在 Next.js Pages Router 下
- Shopify Embedded 壳层、国际化路由、配置读取和最小测试基线已落地
- V3.0 已经解决环境隔离、导航优化、骨架屏、Webhook 基线和脚本统一等问题

当前仍存在以下差距：

- 缺少对安装链路和首屏性能的统一观测，无法稳定量化 `LCP`、首屏可见时间和页面加载瓶颈
- 本地联调仍依赖环境手工切换或直连，缺少统一代理层来解决 `CORS`、header 透传和平台转发调试问题
- 内部插件 `domDagic` 没有标准化接入位，后续项目复用时容易出现接入方式不一致、失败影响主链路、配置分散等问题
- 模板中尚缺少一个可持续补充优化和问题清单的统一技术文档入口

## 3. V4.0 版本定位

V4.0 采用分层路线推进：

- `P0`：先完成模板基线建设，定义统一接入规范、配置模型、脚本入口和最小可验收能力
- `P1`：在 P0 的基础上补齐更强的开箱即用能力，减少业务项目二次集成成本
- `P2`：补充增强型优化项和治理项，用于版本后续迭代或增量纳入

该版本的核心主题定义为：

**安装链路性能观测 + 本地联调代理 + 内部插件标准接入**

## 4. 版本目标

### 4.1 总体目标

- 让模板具备可量化的安装链路性能观测能力
- 让本地开发联调方式从“环境约定”升级为“工具能力”
- 让内部插件接入从“项目自定义实现”升级为“模板标准能力”
- 让 V4.0 文档本身成为团队补充优化和问题处理的承接入口

### 4.2 成功标准

- 新项目基于模板初始化后，可以采集关键 `Web Vitals` 和安装链路时序
- 本地开发可以通过统一代理 server 完成平台和后端联调，不依赖临时改代码规避跨域
- `domDagic` 可以按统一配置和生命周期接入，失败时不阻塞主链路
- 团队成员可以继续在文档中补充新增优化项和历史问题，并保持统一结构

## 5. 非目标

以下内容不属于 V4.0 首轮必须范围：

- 不重新进行大规模目录重构
- 不强制在 V4.0 将所有共享能力抽离到 `packages/*`
- 不要求一次性建设完整性能平台或完整可视化看板
- 不在模板中内嵌过多业务特定逻辑
- 不将 `domDagic` 绑定为不可关闭的强依赖

## 6. 范围总览

### 6.1 P0 必做

- `Web Vitals` 指标采集基线
- 安装链路关键阶段打点与上报协议
- 本地开发代理 server 的统一脚本和配置模型
- `domDagic` 插件接入位、配置开关、失败隔离和 demo
- 配置字段对齐、最小 smoke test、文档和验收清单更新

### 6.2 P1 增强

- 默认接通内部监控出口或统一上报端
- 提供更完整的本地代理调试能力和环境模板
- 提供 `domDagic` 开箱 preset，减少业务项目额外接线工作
- 增加版本化性能阈值和回归检查

### 6.3 P2 候选

- 更细粒度性能归因能力
- 自动生成性能基线报告
- 代理层 mock 能力、录制回放能力
- 插件市场化或多内部插件标准接入模型

## 7. 核心需求一：接入 Web Vitals 指标优化安装链路提升 LCP

### 7.1 目标

建立模板级性能观测基线，重点观测 Shopify App 安装和首次进入时的页面加载体验，优先解决 `LCP` 不可见、不可量化、不可回归对比的问题。

### 7.2 问题定义

当前模板虽然已有骨架屏和嵌入式壳层，但缺少统一性能采集能力，导致：

- 无法区分白屏、骨架出现、业务内容可见分别发生在什么时间
- 无法判断瓶颈来自 Shopify 跳转、iframe 首屏、前端渲染还是首个业务接口
- 无法对不同模板版本、不同页面、不同环境的 `LCP` 改善效果做稳定对比

### 7.3 P0 需求

- 模板默认采集标准 `Web Vitals`：
  - `LCP`
  - `INP`
  - `CLS`
  - `FCP`
  - `TTFB`
- 模板补充安装链路关键阶段打点，至少包含：
  - `install_entry_arrived`：进入 Shopify entry/callback 链路
  - `install_callback_completed`：完成平台 callback 返回
  - `embedded_shell_visible`：Embedded 壳层可见
  - `first_business_response_ready`：首个业务接口完成
- 指标事件统一字段至少包含：
  - `metricName`
  - `value`
  - `rating`
  - `route`
  - `locale`
  - `appName`
  - `shop`
  - `buildVersion`
  - `environment`
  - `installPhase`
  - `traceId`
- 采集逻辑与具体上报后端解耦，允许先上报到现有接口或保留统一 adapter 层
- 模板需支持按环境开关性能采集，避免本地开发和测试时的无效噪音
- 文档中需明确 `LCP` 的观察对象和计算边界，避免不同项目理解不一致

### 7.4 P1 需求

- 增加更细粒度的指标归因能力，例如页面元素、资源和阶段级归因
- 将 `Web Vitals` 与发布版本、环境、入口页面关联，用于回归对比
- 为关键安装链路定义模板推荐阈值，形成发布前性能检查项

### 7.5 验收标准

- 模板运行后可稳定产出标准 `Web Vitals` 事件
- 安装链路至少可看到 4 个关键阶段的时序数据
- 能区分标准性能指标和自定义链路指标
- 文档中明确说明采集边界、字段含义和开关方式

## 8. 核心需求二：本地开发代理 server

### 8.1 目标

为模板提供统一的本地联调代理能力，降低环境切换成本，解决 `CORS`、跨域 header、cookie 透传、平台转发联调和目标地址切换等问题。

### 8.2 问题定义

当前本地联调更多依赖环境配置和直连/代理切换约定，容易出现以下问题：

- 开发人员为了联调临时改代码、改接口地址或绕过跨域
- 平台 entry/callback、后端 API、本地前端之间的目标地址切换不统一
- 不同项目对本地代理的实现方式不一致，难以沉淀模板经验

### 8.3 P0 需求

- 在仓库级提供独立的本地代理 server 能力，不与页面路由代理混用
- 根目录提供统一脚本入口，建议至少包含：
  - `pnpm dev:proxy`
  - `pnpm dev:admin:proxy`
- 代理 server 至少支持以下转发能力：
  - 后端 API 转发
  - Shopify entry/callback 平台转发
  - 自定义 header 透传
  - cookie 与 query 透传
  - 目标 upstream 按环境切换
- 代理 server 至少支持以下调试能力：
  - 打印请求路径和目标地址
  - 输出错误日志
  - 在本地清晰标记当前命中的 upstream 环境
- 代理配置必须统一来源，不允许将代理目标散落在多处常量或多个私有脚本中
- 文档中需要明确代理模式与直连模式各自适用场景

### 8.4 P1 需求

- 支持更细粒度路由规则，例如按路径匹配不同 upstream
- 支持更完善的调试辅助能力，例如请求头差异观察、简易 mock 或 fallback
- 为团队常见环境提供默认配置模板

### 8.5 验收标准

- 新项目基于模板可以通过统一脚本启动本地代理联调
- 业务开发无需为跨域联调临时改动正式请求代码
- 代理目标、路由规则和启动方式在文档中可查且可复用

## 9. 核心需求三：接入 domDagic 内部插件

### 9.1 目标

将 `domDagic` 作为模板标准能力接入，但保持其为可配置、可关闭、可隔离的内部插件，不把业务定制逻辑硬编码进模板主干。

### 9.2 问题定义

如果没有统一接入规范，后续项目接入内部插件时容易出现：

- 初始化时机不一致
- 配置来源分散
- 插件异常影响首屏或主流程
- 项目之间接入代码重复，难以维护

### 9.3 P0 需求

- 模板提供标准 `domDagic` loader 或 provider 入口
- 明确插件初始化时机，至少需要区分：
  - runtime config 已加载
  - Embedded 上下文已可用
  - 页面可安全执行浏览器侧 DOM 能力
- 插件接入必须支持环境开关和配置注入
- 插件加载失败时不得阻塞页面主流程，必须具备失败隔离机制
- 模板中提供最小 demo 或示例接入代码，说明如何注册和关闭
- 文档中明确以下内容：
  - 插件职责边界
  - 初始化顺序
  - 配置字段
  - 错误处理策略

### 9.4 P1 需求

- 为业务项目提供开箱即用 preset
- 支持插件版本或能力开关扩展
- 在不增加主干复杂度的前提下，为后续更多内部插件预留一致接入模型

### 9.5 验收标准

- 基于模板的新项目可以按统一方式启用或关闭 `domDagic`
- 插件异常不会导致应用首屏不可用
- 插件接入说明、配置说明和最小示例齐备

## 10. 其他优化与问题处理

本章节用于承接除三项主线外，仍适合在 V4.0 周期内纳入的优化项和问题处理项。建议按“问题、影响、建议方案、优先级、责任人”补充。

### 10.1 建议默认纳入的共性优化

- 配置 schema 校验
  - 对齐 `.env.example`、运行时配置、服务端配置和 README 字段定义
- 构建版本注入
  - 将 `buildVersion` 注入前端运行时，用于关联性能事件和发布版本
- 最小 smoke test
  - 至少验证安装入口到嵌入式壳层可见的主链路
- 发布检查清单更新
  - 将性能、代理、插件开关和配置合法性纳入检查项
- 监控与错误上报收口
  - 避免性能指标、客户端错误和插件异常各自走不同风格的上报模型

### 10.2 团队补充规则

后续补充项建议统一采用以下格式：

- 问题标题
- 场景描述
- 当前影响
- 建议处理方案
- 优先级：`P0 / P1 / P2`
- 是否纳入 V4.0 首轮
- 提出人 / 负责跟进人

### 10.3 当前建议补充收集的方向

- 安装链路白屏或二次重定向问题
- `host / shop / locale` 丢失问题
- 本地代理和测试环境切换冲突问题
- Shopify App 审核相关配置检查项
- 运行时配置漂移问题
- 模板示例代码、占位资源和过期脚本清理问题

## 11. 对现有仓库的影响建议

V4.0 预计主要影响以下模块：

- `apps/admin/pages/*`
- `apps/admin/components/*`
- `apps/admin/lib/monitoring/*`
- `apps/admin/config/*`
- `apps/admin/docs/*`
- 根目录 `README.md`
- 根目录 `docs/release/*`
- 仓库级 `scripts/*`

建议遵循以下原则：

- 页面级国际化代理继续保留在 `apps/admin/proxy.ts`
- 本地开发代理 server 独立于 `apps/admin/proxy.ts`
- 性能采集、插件接入、运行时配置尽量围绕现有 `apps/admin` 能力演进
- 只有在出现第二个稳定消费方时，再考虑抽离到 `packages/*`

## 12. 建议交付物

### 12.1 P0 交付物

- 一份可执行的 V4.0 实施计划
- 一份模板级性能事件模型说明
- 一套本地代理配置与启动脚本
- 一套 `domDagic` 接入规范与示例
- 更新后的 README、技术设计文档和发布检查清单

### 12.2 P1 交付物

- 默认可运行的性能上报出口
- 更完善的代理联调体验
- `domDagic` 开箱 preset
- 模板性能阈值与回归检查机制

## 13. 验收口径

V4.0 验收建议按以下口径执行：

- 功能验收
  - 三项主线能力均具备模板级接入方案
- 工程验收
  - 新项目可按文档说明启动、联调和验证
- 文档验收
  - README、技术设计、发布检查清单与实际能力一致
- 稳定性验收
  - 插件失败不阻塞主流程
  - 代理联调不要求业务代码临时改造
  - 指标采集可开关、可追踪、可解释

## 15. 结论

V4.0 应聚焦于“可观测、可联调、可扩展”三件事：

- 用 `Web Vitals` 和安装链路指标把性能问题看清楚
- 用本地代理 server 把联调方式标准化
- 用 `domDagic` 标准接入能力把内部插件复用沉淀下来

在此基础上，保留“其他优化与问题处理”作为团队共建入口，让 V4.0 不只是三项功能需求，而是一轮面向模板可持续演进的工程升级。
